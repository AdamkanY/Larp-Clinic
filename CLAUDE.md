# Trial-Radar – agent guide

Trial-Radar is the HSG Computer Science group project (English track). It predicts the risk that a clinical
trial is terminated early, using only information known at the trial's initial design. Data comes from
ClinicalTrials.gov (API v2, pulled by script). The deliverable is a Streamlit app where users can (1) search ongoing trials via the
ClinicalTrials.gov API v2 and see the predicted termination risk, (2) see which factors drive each prediction,
(3) explore interactive visualisations of the historical data, and (4) play a game: guess which of two
historical trials was terminated, scored against the model.

Supervisor grading priorities (Dominik Buchegger): a **working ML model**, **real user interactivity**,
**plenty of visualisations**.

Team: Adam Kanouni (ML model), Simon Seidl (data pipeline), Dominic Haibach (evaluation & explainability),
Matteo Kaufmann (app & UX), Raphael Schmid (visuals, game, video).

Deadline **Dec 16, 2026**. Internal target: final version by **Dec 11**, feature freeze **Dec 6**.

Stack: Python, pandas, scikit-learn (possibly LightGBM), SHAP or permutation importance, Streamlit,
deployed on Streamlit Community Cloud.

## Non-negotiables

1. **Label:** `TERMINATED = 1`, `COMPLETED = 0`. Everything else (WITHDRAWN and ongoing statuses `RECRUITING`,
   `ACTIVE_NOT_RECRUITING`, `NOT_YET_RECRUITING`, `ENROLLING_BY_INVITATION`) is dropped for training. Ongoing
   trials are only scored by the app, never trained on.
2. **No leakage.** Use only features known at design time. Never use the reason the trial stopped, any date
   except the start date (completion, primary completion, last update, results dates), results, or enrollment.
   - **Enrollment is permanently excluded** (finished trials report actual counts, which leak the outcome).
   - **Locations / number of sites are excluded from v1** (sites are added after start).
   - `build_features` reads only an explicit list of API fields (see `data/raw/CLAUDE.md`); keep it that way.
3. **Split by start date**: keep trials starting 2008-01-01 to 2019-12-31. Train = start 2008-2016, test =
   start 2017-2019. Drop start dates >= 2020 and invalid ones. Never a random split.
4. **Metrics:** report ROC-AUC and PR-AUC, not accuracy. Classes are imbalanced (~11% terminated).
5. **One feature function:** the app and the training code must use the same feature-building function
   (`build_features` in `src/features.py`), which takes one API study record.
6. **Raw data is not committed.** `data/raw/` is git-ignored; regenerate it with `python src/fetch_data.py`,
   then `python src/build_dataset.py` for `data/processed/trials.parquet`.

## Conventions

- PEP8; a docstring on every function; comments explain *why*, not what.
- Small commits with clear messages.
- No notebook code is imported by the app.
- Relative paths only (never `/Users/...`).
- Update `requirements.txt` whenever a library is added.
- Raw data is not in git (no LFS any more); regenerate it with `src/fetch_data.py`.

## How to keep this file current

The guides are the team's shared memory, so keep them true after every prompt that changes something, in the
same commit as the change:

1. **The folder's `CLAUDE.md`:** a row for every new file, no row for a deleted one, and a corrected row when
   what a file does or holds changed. Mark planned files "(expected)" and drop the marker once they exist.
2. **This file:** a dated line under "Recent changes" for anything notable; move Status, Roadmap and Open
   decisions when they change; a directory-map row for every new top-level folder.
3. **Numbers** quoted in any guide (dataset sizes, metrics) whenever the data or a model is rebuilt.

This is checked automatically. `.claude/settings.json` runs `.claude/hooks/check_claude_md.py` before Claude
ends each turn. It blocks the stop once when a file has no row in its folder's table, a table lists a file
that is gone, an "(expected)" file now exists, or files changed since the last check while their guide and
"Recent changes" did not; Claude then updates the guides or says why nothing needed to change. It never blocks
twice in a row and stays silent if something goes wrong (it needs `python3` and `git`). People working without
Claude run `python tests/test_claude_md.py`, which does the table part of the same check.
